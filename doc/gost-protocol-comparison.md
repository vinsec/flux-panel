# 相同协议屏蔽：GOST 与 v5.5 内核转发对比

结论：本地少量规则场景下，内核模式在150Mbps传输时的CPU较低，持续TCP/UDP及新连接首回复延迟较小；三者都完成设定速率与收包检查。25Mbps下占用很低，进程CPU差距小，整个测试核CPU并非每项都由内核模式占优，不能据此声称普通视频能快数倍。

测试仅本机Fusion隔离私网，无线上SSH、部署、数据库或配置改动，无GZ入口或公网数据转发。

CPU百分比按一个测试核=100%；转发进程CPU不包含全部转发成本。内核处理可能计入收发进程/软中断，所以同时给出整个测试核CPU。单核固定负载及虚拟机数值不能当作生产硬件额定能力。

每种逻辑规则数均由GOST、原生nft和保留iptables轮换顺序各跑三轮。全部HTTP/TLS/SOCKS开关为1，并用真实TCP的HTTP/TLS/SOCKS4/5帧验证阻断、用不透明TCP/UDP验证透传；共90项预检记录。负载是模拟加密代理外层的不透明字节，不包含SS加解密，也不是访问真实视频网站。直连TLS/HTTP会被这些开关阻断，不能用它们直接冒充加密代理外层负载。

## 新连接：必须区分处理成本和出口端口压力

主对照的CPS是每组连续10万次“TCP连接+64字节回显”，包含建立后端连接；不是仅计监听器accept。每5000次切换客户端源IP，避免客户端TIME_WAIT端口空间耗尽。GOST仍需从单个路由器出口IP向同一后端IP:port主动连接，内核NAT则不为每条流创建本机上游TCP socket。

GOST第一批尚未堆积端口时约6–7k/s，后续降至约0.8–0.9k/s；独立perf诊断中约82.8%的调用树样本位于`__inet_hash_connect`，系统态CPU明显增加。另做只改变隔离路由器首选源地址、每5000次分散到一个新的私网IP的诊断，无CPU采样的三次总中位数为 **6965 次/秒**。因此不能把主表约1.1k对1万概括成所有条件下的纯处理能力相差约9倍。

分散源IP诊断改变了出口资源条件，只用于定位原因，不是线上调优指令或原样单出口配置的性能保证。普通少量长连接不会持续制造这种端口压力。表中CPS是当前冻结版本与配置的结果，GOST和内核代理的编译器版本也不同，不能做纯算法归因。

## 日常下载、视频、复用与测速

规则数、并发连接数、每秒新连接数是三个不同量。固定一条转发端口可同时承载很多TCP/UDP会话，不意味着所有请求只走一条连接。

大文件可在一个或数个长连接上持续传输，数据包/数据块不等于新TCP。HTTP/1.1默认支持长连接；HTTP/2允许同一连接多个并发流，但不同目标、切CDN、重试、空闲超时、网络切换仍可能新建连接。[HTTP/1.1](https://www.rfc-editor.org/rfc/rfc9112.html#section-9.3)、[HTTP/2](https://www.rfc-editor.org/rfc/rfc9113.html#section-5)

代理层复用另算：普通TCP转发和SS2022请求流不会仅因经过同一节点就自动把所有应用目标合并为一条TCP；额外mux取决客户端。本次没有读取实际客户端配置或采集真实使用流量，不声称该用户实际启用mux或实际CPS。[SS2022请求流格式](https://shadowsocks.org/doc/sip022.html)

普通吞吐测速常用一个或若干并行数据流持续传输，不是每秒创建成千上万连接。iperf3有控制连接和独立数据连接，`-P`控制并行流；本次额外验证了单流和4流下载收包。批量节点URL/延迟探测、多用户短请求、BT/P2P等更可能形成建连突发。HTTP3/QUIC走UDP，不能直接由TCP CPS评价。[iperf3](https://software.es.net/iperf/invoking.html)、[QUIC](https://www.rfc-editor.org/rfc/rfc9000.html)

量纲示例：假设10条连接各持续60秒，持续轮换的平均速率约0.17CPS，启动时仍会突发建立10条。这不是对真实应用流量的测量。对题述普通单人代理下载/视频，应优先看所需带宽能否跑满、固定带宽下CPU、长时间稳定和丢包/抖动；即便GOST的资源压力场景CPS也不应直接理解为日常瓶颈。
