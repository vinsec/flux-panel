# 转发引擎第一批：隔离验收与性能对照

2026-10-26。基准清单为 `forward-engine-roadmap.md`，本批实现 01–09、28。运行时代码提交 `2821124`，比较基线为 `7ed1955`。新增能力的具体语义、安装和回滚用法见 [v3 说明](forward-foundation-v3.md)。

没有向生产部署，也没有执行生产数据库迁移或发布 GitHub Release。所有业务测试均在一次性容器的私有 veth/netns 中，使用 `--network none` 或 Docker internal 网络；没有经过 qcloud 广州入口。SSH/SCP 管理连接显式禁用 ProxyJump。

## 功能、恢复与交付

<!-- VALIDATION_MATRIX -->

面板回归使用真实 Spring Boot JAR、临时 MySQL、真实 Agent 和 GOST 二进制，客户端独立通过 TCP/UDP 与目标交互；不以 systemd active 或规则存在代替业务验证。AMD64 使用 MySQL 5.7，ARM64 使用 MySQL 8.2。节点仍仅运行 Go Agent，不需要 Java。

覆盖已有连接与新连接暂停、同目标不同转发隔离、恢复与累计值单调、转发/用户/授权账本一致、累计重放去重、普通配额暂停、多节点共享 64 KiB 额度、双向消耗、离线额度关闭、重连收敛，以及旧 GOST 创建/暂停/恢复/统计与跨引擎端口冲突回归。

独立内核夹具覆盖 9 个事务退出点；维护夹具覆盖 7 个中断点、重复执行、校验和、权限 600、历史 v1/v2 实际迁移、保留最新累计值的回滚、离线关闭保护、面板结算确认和仅移除所属规则的卸载。安装夹具验证离线包、错误 pin 拒绝、重复安装、真实转发、升级启动失败后旧二进制/状态回滚和再次升级。内核保护检查外部集合、旧版 live 规则、mark 冲突、丢状态和保留外部策略。

IPv4 通过中间路由器自然产生 fragmentation-needed，并验证 4000 字节 UDP 分片与暂停边界。IPv6 在专用夹具验证控制编译器的 Packet Too Big、源端分片重组和暂停保护；**产品级 IPv6 转发仍关闭**，域名也仍关闭，分别属于第 12、11 项。

Go race/vet 通过。Java 10 个单元测试通过；原应用上下文测试受 `FLUX_TEST_DB=1` 门控，常规构建跳过它，完整上下文由上述真实 JAR 启动与重启回归实际覆盖。GOST 的两种架构另对确切二进制验证 WS/WSS 连接与初始 HTTP/HTTPS 配置上报。

ARM 原生验收使用独立 Lima VZ Debian VM（aarch64、Linux 6.1），没有用 QEMU 跨架构容器替代原生内核。Docker Desktop 当前内核缺少所需 `hash:ip,mark` 类型，预检明确拒绝，未绕开检查。另在任务 VM 内使用实际 PID 1/systemd，服务附着私有 router netns，验证低端口、控制/统计新鲜度和沙箱权限。

## 规模与修复

<!-- SCALE_RESULTS -->

内核规模夹具通过一个异步批次建立 10,000 条配置，验证分页快照、幂等重试、1,000/10,000 条整体暂停与恢复、批量删除和已有连接清理。批量回收 19,998 个已确认计数、9,999 个 token 时，另一个 TCP 连接连续完成 1,500 次回声；不通过关闭统计或暂停支持换性能。

本批规模验证修复了三处实际问题：计数回收逐条导出的平方级开销；超过 10,000 条待结算记录的报告超限；删除空规则时逐条启动 conntrack 导致超过租期。现在回收批量导出/删除，报告轮转分页，连接清理只覆盖确定撤销且存在引用的 token 前缀。

整体 HTTP 对账包括分页、数据库版本分配、加解密、异步排队和内核应用，不能将它全部记作业务屏障时长。规模场景不再假设新建的 5 秒权限足够完成初始化；离线夹具按实际期限等待，并区分无限额持续转发与短期 credit 到期关闭。早期失败的证据保留在任务工作目录，未拿失败轮补足最终通过轮。

10,000 条面板规模夹具包含 9,998 条管理员豁免规则与两条普通配额转发；这证明该配置规模下的对账和活跃租约，而非 10,000 个活跃有限额转发同时续租的容量。多用户高并发、长稳态、物理网卡 PPS 与掉电压力仍归第 20 项。

## 同拓扑性能对照

与上一轮相同的 qcloud-sg 私有 client/router/target 拓扑，MTU 1500；容器 0.75 核、512 MiB、nice 19、低 CPU 权重；controller CPU 0、端点 CPU 1。保留默认 TSO/GSO 开启、GRO 关闭，完整记录 offload、CPU、steal 和 throttling。没有生产面板/数据库测试进程与性能阶段并行。

比较 GOST、未改动的 ipset v2 和本批 v3。普通路径使用相同 5 秒报告周期；另单独测试 v3 内核 credit 路径，使用 1 秒采样与频繁 TTL 续租，不能把两种配额语义混为同一负载。每组交错顺序、三轮；TCP 定长 64 MiB 以接收端收齐回执为准，UDP 为固定发送上限；同速率 TCP 为 150 Mbps、5 秒。

CPU 主表为整个测试 cgroup 的核秒/GiB，包含端点和控制器；另保留测试核 system/softirq 结果，后者混入共享主机背景工作。Agent 进程接近零 CPU 不代表内核没有成本。GOST 与 Agent 的系统监控能力也不等价，不能把所有管理开销差异归因于数据搬运。

常规 TCP/UDP 仍走有界分类与哈希计数路径；新的 ICMP 错误树随规则规模增加结构项，因此专属 filter 的总规则数会增长，不能宣称所有规则总数为常量。计数导出表只测两个 ipset 原始导出，不包含 Go 解析、fsync、HTTP 与面板 SQL。

结果适用于本次隔离条件。三轮与共享宿主机不能证明所有内核、长期公网、物理 PPS、多核或所有指标均提升；实际范围和波动保存在原始 JSON/CSV。
