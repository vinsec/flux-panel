## 当前基线

已有：节点/隧道选引擎，旧数据默认 GOST；独立 Go Agent；WSS/HTTPS 控制与统计；外部入口单目标 IPv4 TCP/UDP；创建、更新、暂停、恢复、删除；已有连接暂停；本地到期；持久化累计计费、重发去重、转发/用户/授权三层账本；面板配额触发暂停；断线后配置对账；同机跨引擎保守端口冲突检查。

## 域名与 IPv6 的统一模型

已实现统一端点、独立监听与目标池模型；面板和 Agent 均做结构化校验。下面是 schema 3 的期望配置示意，完整字段与限制见 v4 文档。

```json
{
  "schemaVersion": 3,
  "id": "1_2_3",
  "revision": 1,
  "enabled": true,
  "listen": {"host": "::", "port": 18000, "family": "dual"},
  "targets": [{"endpoint": {"host": "origin.example", "port": 443}, "weight": 1}],
  "selection": "fifo",
  "dnsPolicy": {"staleMillis": 30000, "drainMillis": 300000}
}
```

一个逻辑转发仍对应一个持久化 token、一个业务 ID、一份配额和账本。desiredRevision 表达用户配置，resolutionGeneration 表达节点解析结果，两者分离。面板保存原始域名；Agent 保存具体解析 IP、TTL、健康状态及正在排空的旧目标。控制接口上报 desired/applied revision、地址族、解析代次、最近成功和错误原因，界面能区分“已保存”和“已生效”。

Java 端统一 Endpoint 解析器，Go 端使用 `net/netip` 与 `net.JoinHostPort`。IPv6 文本规范化，带端口输入必须为 `[2001:db8::1]:443`；IP 常量与域名明确区分。本轮对带 zone 的目标和 link-local 目标明确拒绝；普通转发不把 `%eth0` 误当域名或规则文本。

### 域名：Agent 解析，内核只处理数字地址

1. Agent 按节点出口环境解析 A/AAAA，避免面板所在地域的 CDN DNS 结果代替节点结果。DNS 客户端需要暴露 RR TTL；Go 的普通 `LookupIPAddr` 不足以直接获取 TTL，使用经过评估的 DNS 协议库或显式 DNS 服务适配器。处理 CNAME 链、截断后的 TCP 回退、超时、取消、最大响应/目标数和 negative cache。
2. TTL 到期前带随机抖动刷新；TTL=0 不长期缓存；临时错误只在明确、有限的 stale grace 内使用最近成功结果，超过期限关闭新连接并显示故障。管理员可选择立即 fail-closed。NXDOMAIN 与超时分开处理，不能无限保留旧 IP。TTL 语义参考 [RFC 1035](https://www.rfc-editor.org/rfc/rfc1035.html)。
3. 首期每地址族选一个稳定的 IP，不随 DNS 响应顺序抖动。后续多目标才增加权重和健康检查。可配置允许的地址范围，防止解析结果无意指向本机管理端口、回环或不允许的内部网段；允许内网目标应是显式策略。
4. 刷新时先准备新 IP 的计数和放行项，再切换新连接 DNAT；旧 conntrack 映射继续使用旧 IP。自动 DNS 刷新不调用现有的 `Forget`，不主动打断已有连接。旧目标继续受同一 token 的暂停控制，等 conntrack 排空或最长保留期后删除。用户明确修改目标时另设“立即切换/排空”策略。
5. 暂停时删除该 token 所有当前与 retiring IP 的放行项；各 IP 的上下行计数汇总到同一业务 ID，刷新不能重置账本。DNS 长期抖动时需限制 retiring 项数量并报警。
6. 域名只用于确定目标 IP，不重写应用层 Host/SNI，不终止 TLS。TCP/UDP 纯转发不能替应用修改证书域名。

不能把 iptables 用户空间“装载时解析一次域名”当作完整域名支持；它没有上述刷新、排空、故障和计费语义。

### IPv6：分别编译两种内核规则，共享生命周期

1. v4 使用 iptables + `family inet` 的集合；v6 使用 ip6tables + `family inet6` 的独立集合和链。二者共享 token，但规则、集合、计数基线按 family 分开保存，报告时汇总；IP/地址族必须参与 key。利用 ipset 现有 inet6 与 mark 支持，避免引入逐包用户态转发；见 [ipset 官方手册](https://ipset.netfilter.org/ipset.man.html)。
2. 首期支持 v4→v4、v6→v6。双栈入口产生两套同族路径，同域名分别选 A 与 AAAA；某一族没有目标时明确禁用该族，不默默改走另一族。纯 DNAT 不创建两条上游连接，不能直接承诺代理式 Happy Eyeballs；该算法涉及地址排序和并发连接尝试，参见 [RFC 8305](https://www.rfc-editor.org/rfc/rfc8305.html)。
3. v6 默认采用可预期的有状态 DNAT/SNAT；具备返回路由时再提供保留客户端源地址的 routed 模式。部署前检查 IPv6 forwarding、出口地址、路由、RA、DAD、邻居发现和 conntrack/NAT 模块。开启 forwarding 可能影响 RA 接收，应按接口核查 `accept_ra`，必要时经部署方案设置为 2；不在 Agent 中静默修改。依据 [Linux IP sysctl 文档](https://www.kernel.org/doc/html/latest/networking/ip-sysctl.html)。
4. 必须覆盖 ICMPv6 Packet Too Big、PMTU、ND 和扩展头/分片。相关 ICMP 错误在独立 RELATED 路径验证正确性和暂停边界，不把所有 ICMPv6 一概丢弃，也不把邻居发现算成某个转发的业务数据。
5. IPv4→IPv6 或 IPv6→IPv4 作为独立 capability：另评估 Jool/NAT64 等内核转换组件，或明确交给 GOST。不能用 iptables/ip6tables 的同族 DNAT 声称已经支持跨族。

验收全部在隔离 netns 内建立可控 DNS 与双栈目标，覆盖低 TTL、CNAME、轮换、NXDOMAIN、解析超时、暂停、配额、DNS 刷新期间旧连接、双栈单族故障、v6 UDP、大包 PMTU 和重启恢复，公网 DNS 与广州入口均不参与压测。

## 推荐实施顺序

第一批处理 01–09、28 中的生产基础，优先 capability/Endpoint、事务恢复、计费/配额边界、回收和 PMTU。域名 11 与 IPv6 12 可以基于统一模型并行开发，但上线依赖前述恢复与计费语义。第二批完成 13–20、29，补齐多目标、路由、限速、监控、客户端与长稳态验收，再执行 10 的灰度上线。21–27 按实际业务需求选择，不把 GOST 已擅长的协议封装强塞给 L4 内核转发。

本清单不把基本暂停、在线配额暂停、重发去重、账本、网页引擎选择重新列为未实现；真正待补的是其明确的新语义、规模和交付边界。
