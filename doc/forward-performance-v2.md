# iptables v2 优化与隔离性能复测

2026-10-25。结论：本轮解决了 100/1000 条规则下的逐包线性扫描退化。v2 用 ipset 哈希集合分离分类、放行与计数，新连接 DNAT 使用固定深度的标记前缀树；暂停、在线配额触发暂停、到期和持久化累计统计均保留。域名、IPv6 和其他缺口本轮提供完整实施方案，尚未开放这些能力。

## 实际实现

- 每个转发分配持久化 16 位 token，连接标记为 `0xf1 | token | 低8位`，本模式只管理掩码 `0xffffff00`，不覆盖低 8 位。失败分配也不复用，避免旧连接或计数串到新转发。
- `FPV2_BIND`：按本机监听 IP、协议和端口哈希取得 skbmark；后续包直接恢复 connmark。通配监听在 apply 时展开为已分配本机 IPv4。
- 首包 DNAT 以 token 的十六进制前缀分成三层，每层最多 16 个分支，叶层最多 16 个 token × 两种协议；不会对全部 N 个转发做首包平铺扫描。
- `FPV2_ALLOW`：目标 IP + token 的独立放行集合。暂停删除该转发项，已有连接两个方向均受控；不会因为外部 ESTABLISHED ACCEPT 而绕过。未使用 flow offload。
- `FPV2_UP/DOWN`：同样按 IP + token 的内核逐项累计字节，不通过每包遍历 N 条计数规则。保留旧目标/删除记录计数，暂停恢复、规则重建不重置。上报仍用 epoch/sequence/累计值和原账本去重，不依赖 conntrack 事件无损投递。
- 批量绑定/策略通过 staging set + swap 切换，单项启停直接增删放行集合。缓存结构摘要，启停/到期不重建 NAT 树；去掉配置变更路径中的重复计数读取。

依据 [ipset 官方手册](https://ipset.netfilter.org/ipset.man.html) 使用原生哈希、逐项计数与 swap；计数项重加可能重置计数，因此实现只增加缺失项。数据面始终由内核处理，Agent 不搬运业务数据。

## 测试隔离与方法

测试运行于 qcloud-sg 一次性容器，`--network none`，client/router/target 三个独立 netns，MTU 1500 的私有 `10.204.0.0/16` veth。controller/root 和 router 均断言无外部默认路由；client/target 默认路由只指向此私有 router。未使用 qcloud 广州入口，也没有公网转发压测。SSH/SCP 管理连接显式 `ProxyJump=none`。

与前轮保持拓扑和资源条件：容器 0.75 核、512 MiB、低 CPU 权重、nice 19；控制器 CPU 0，端点和转发进程 CPU 1。2 vCPU 测试机与其他服务共享，存在调度噪声。veth 的 TSO/GSO 为开启、GRO 为关闭，沿用默认状态并完整记录，不能将本次结果当成禁用网卡 offload 的物理包速率。

GOST、未修改的 v1、v2 使用同一端点，三种顺序交错、每组各三轮；热服务排序在末端。TCP 主表每次 64 MiB，接收端收齐后回执，严格核对收发字节一致；基础组另测下载/四流。45 个定长传输、36 个 UDP 案例、18 个固定速率 TCP 案例、45 个延迟案例；每个计数组合导出十次。三个二进制均保留统计，Agent 周期 5 秒。

## TCP 短传输：三轮中位数

Gbps 为接收端回执确认的应用有效数据速率；CPU 为整个测试 cgroup 核秒/GiB，包含端点和控制器，不是转发器进程独占 CPU。p95 合并三轮长连接回声样本：基础组每引擎 1500 个，规模组各 900 个。

| 转发数 | 引擎 | 上传 Gbps（最小–最大） | cgroup 核秒/GiB | TCP 回声 p95 ms |
|---:|---|---:|---:|---:|
| 2 | GOST | 5.639（5.044–9.518） | 1.431 | 0.324 |
| 2 | iptables v1 | 12.930（12.313–14.834） | 0.783 | 0.203 |
| 2 | iptables v2 | 14.285（13.951–15.624） | 0.731 | 0.255 |
| 100 | GOST | 6.044（4.868–8.927） | 1.249 | 0.426 |
| 100 | iptables v1 | 3.231（2.511–3.547） | 2.310 | 0.374 |
| 100 | iptables v2 | 15.930（14.606–16.936） | 0.660 | 0.249 |
| 1000 | GOST | 7.050（2.725–8.922） | 1.405 | 0.404 |
| 1000 | iptables v1 | 0.265（0.263–0.281） | 24.737 | 2.027 |
| 1000 | iptables v2 | 14.373（14.338–16.394） | 0.726 | 0.232 |

1000 条规则下，v2 吞吐为 v1 的 **54.2 倍**，为 GOST 的 **2.04 倍**。短传输 cgroup CPU/字节较 v1 降低约 97.1%。短传输很快，CPU burst、throttling 和共享主机噪声会影响数值，因此下面另列同速率结果。

两条规则时，v2 的 pooled p95 为 0.255 ms、v1 为 0.203 ms；没有证据支持“所有规模、所有指标都提升”。GOST 三轮波动也较大，表中保留范围，不从三轮推断严格统计显著性或线上容量。

## 同速率 CPU：150 Mbps、每轮 5 秒

每次传输覆盖正常的 5 秒采样周期；保留解析、状态落盘与上报工作。仍为三轮中位数，整组 cgroup 核秒/GiB；不同计费口径不影响此处统一的应用负载分母。CPU 对比包含各自管理实现的差异：GOST 含系统监控，新 Agent 尚未提供同等系统指标，不能将所有 CPU 差异归因于数据搬运本身。

| 转发数 | 引擎 | 接收 Mbps | cgroup 核秒/GiB | 平均占一核百分比 |
|---:|---|---:|---:|---:|
| 2 | GOST | 150.15 | 3.926 | 6.83% |
| 2 | iptables v1 | 150.15 | 3.266 | 5.69% |
| 2 | iptables v2 | 150.15 | 3.665 | 6.39% |
| 1000 | GOST | 150.14 | 4.476 | 7.80% |
| 1000 | iptables v1 | 149.97 | 30.926 | 53.30% |
| 1000 | iptables v2 | 150.15 | 3.553 | 6.18% |

1000 条规则处理相同速率时，v2 CPU/字节较 v1 降低 **88.5%**，较 GOST 降低 **20.6%**。两条规则时 v2 的固定管理成本略高于 v1，不能忽略。CPU 1 的 system/softirq、steal、空闲窗口和 cgroup throttling 均在原始 JSON 中；整核采样混入后台工作，不能将 Agent 进程接近 0 的 CPU 当成内核没有成本。

## 计数导出与规则规模

只测原始内核导出加相同 Python 编排：v1 一次 `iptables-save -c -t filter`，v2 两次 `ipset save`。不含 Go 解析、持久化、HTTP 或面板 SQL，不把它称为完整统计链路成本。后台导出仍随集合条目数 O(N) 增长，消除的是逐包 O(N) 扫描。

| 转发数 | 引擎 | mangle / filter 专属规则数 | 导出 KiB | 导出 wall ms | cgroup CPU ms |
|---:|---|---|---:|---:|---:|
| 2 | iptables v1 | 5 / 10 | 2.09 | 4.62 | 4.55 |
| 2 | iptables v2 | 5 / 8 | 0.80 | 7.90 | 7.23 |
| 100 | iptables v1 | 201 / 402 | 82.46 | 15.16 | 14.99 |
| 100 | iptables v2 | 5 / 8 | 17.25 | 7.21 | 7.00 |
| 1000 | iptables v1 | 2001 / 4002 | 820.74 | 155.03 | 116.94 |
| 1000 | iptables v2 | 5 / 8 | 168.42 | 12.57 | 12.92 |

规则数含所有权 RETURN 标记；首包 NAT 仍随配置增加结构条目，但每次只走有界分层路径。1000 条时导出约 155→12.6 ms，导出 CPU 约 117→12.9 ms。两条时因 v2 导出两个集合，7.9 ms 高于旧版 4.6 ms；后续可用 netlink 批处理降低固定开销，不能宣称采样在小规模也更快。

|---:|---|---:|---:|
| 2 | GOST | 49.971 | 4.996 |
| 2 | iptables v1 | 49.976 | 4.997 |

| 1000 | iptables v1 | 13.957 | 0.576 |
| 1000 | iptables v2 | 49.973 | 4.997 |

1000 条时旧版在这两档只达到约 13.96/0.576 Mbps，新版与 GOST 达到设定速率。旧版的接收丢包率可能为 0，但发送端本身没有达到设定发送速率，不能把“0 丢包”理解成已满足负载。基础组新连接首响应、UDP 回声、下载和四流结果全部保留于 JSON/CSV。

## 独立功能与保护验证

同一个最终 amd64 二进制：真实 Spring Boot 面板 + 一次性 MySQL + Python 客户端在 nft/legacy 后端各 35 项通过；另在无网络容器各 5 项拒绝接管保护通过，合计每后端 40 项。覆盖新旧 TCP/UDP 暂停、同目标不同转发隔离、暂停恢复计数单调、三层账本、重复报告、配额暂停、离线到期、目标更新、重启恢复、删除后 NAT 树清理、真实 GOST 回归、外部集合/标记冲突、live v1 升级拒绝，以及零计数但已有 NAT 树时的丢状态拒绝。

Go race、go vet、定长传输工具与测试脚本语法检查通过。arm64 已交叉编译，未声称本轮在 ARM 内核做过原生验证。Java 面板 JAR 沿用上轮已编译产物，后端/前端业务代码本轮未改动。

## 交付边界与证据

所有性能阶段连同失败校准已知负载合计 **4.775 GiB**，在显式 5 GiB 总预算内，全部通过私有 veth；不是广州入口流量，也不是公网跑量。主数据经独立汇总脚本校验：81+18 个吞吐案例、45 个延迟案例、6 个十次计数导出组合完整，分组均三轮，TCP 收发一致，二进制哈希一致，无 failed 标记，最终 metadata 有正常完成时间。

两处测试编排问题单独保留：首次将 UDP iperf 控制流误指向 TCP 专用定长端点，失败校准未入主结果，其已确认 192 MiB 纳入总预算；后续主矩阵已经完整正常结束，但外层 shell 因运行时更新其脚本文件导致收尾 EOF，未取得 console 副本。完整 JSON、45 个 receiver-ack 案例、81 个逐项有效结果及最终完成 metadata 均已独立校验；固定速率阶段使用稳定脚本并正常退出。没有用失败轮填补三轮数据。

生产面板、前端、MySQL、Redis 的容器 ID/镜像/启动时间前后一致；测试容器和网络已清理。主机防火墙快照唯一差异为 fail2ban 自行新增一条 SSH 封禁，日志时间与该差异吻合；其余规则一致，无本项目 FP_* 测试链部署到主机。没有修改生产面板数据库或启用新引擎。

新增依赖是标准 netfilter 的 ipset。当前仍为实验版：live v1 规则拒绝直接覆盖升级；主机掉电未落盘窗口、跨表/集合原子性、token 与历史计数回收、精确离线配额、PMTU/ICMP 完整矩阵等仍有明确待办。完整 **29 项待实现项、逐个实现方案、依赖和验收条件**，以及域名/IPv6 设计，见 `forward-engine-roadmap.md`。
