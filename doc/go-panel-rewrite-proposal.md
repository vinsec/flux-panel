## 建议决策

最终用一个 Go 面板进程替代 Java 后端，保留当前 React/Vite 前端、MySQL 数据和两类 Agent。
范围已确定：GOST 保留，内核 Agent 只保留原生 nftables；
不再开发、发布或测试 iptables、iptables-nft、iptables-legacy 后端，也不提供自动回退。
代码可以新写，验收按模块分批进行；首批不直接替换线上，不同时重做界面、数据库和节点协议。
Go 统一工具链及部署形式是可预期收益；内存、CPU、启动耗时和请求延迟的收益要用同环境测试确认，暂不承诺倍数。
面板语言变化不会直接提高已经在 Linux 内核中转发的业务吞吐。

采用模块化单体，建议目录 `panel-go/`，独立 `go.mod`；`node-agent/` 保持独立发布。
在独立 `feat/panel-go-native` 工作区实现，不在共享内核转发分支混入实现。
首期保持现有部署的前后端边界，最终可选一个 Go 可执行文件附带前端静态资产；不要求引入 Redis、消息队列或微服务。

## 能否完整替代 Java

可以把“完整替代 Java 的全部保留功能”作为最终交付目标，现有功能没有必须依赖 Java 语言才能实现的要求。
这不是只重写用户、节点、隧道几个管理页面：登录鉴权、验证码、OpenAPI、GOST 控制、nftables Agent 控制、
流量计费、共享额度、限速、协议屏蔽、定时任务、安装配置及运维行为都属于交付范围。
用户明确移除的 iptables 支持属于主动删减，不要求在 Go 中恢复。

分批开发不等于每一批都可替换 Java。第 1–4 批是中间成果，第 5 批逐项验收通过后，才称为完整替代。
本轮已新增完整 Go 模块；完整清单从 `a08e3d8` Java 源码逐项盘点，包含前端没有直接展示的接口和任务。

## 前面几项要求，用实际例子说明

这些是实现时应做到的要求，不需要用户决定内部锁、事务或连接管理的写法。

1. **换面板时只让一边管事。** 测试期间 Go 使用单独的测试数据库；正式替换时，先让 Java 停止改数据、
   下发命令和执行定时任务，再让 Go 接手。避免一份流量被收两遍，或凌晨额度被重置两遍。
   首次发布推荐整个面板一起切换，暂不做一半节点归 Java、一半归 Go 的混合运行。
2. **断线或超时后，页面必须能恢复成真实状态。** 例如“暂停规则”已在节点成功，但回执丢了，面板不能直接当作没暂停，
   也不能一直显示成功而不核实。重连后应核对节点实际状态，再安全完成或重试操作。
3. **原生累计流量只算一次，额度不能多发。** 同一份 100 MB 累计报告重发三次，仍只记 100 MB；多个节点共享 1 GB 额度，
   不能每个节点各拿到完整的 1 GB。面板崩溃重启、跨日重置时也要遵守同样规则。旧 GOST 保留其 delta 协议，没有报告编号，不能承诺新增任意重试去重能力。
4. **性能拿实测说话。** 用相同机器、数据库和负载比较 Java 与 Go；先要求功能正确、没有明显变慢，再看内存和速度能改善多少。
   具体测试时长和允许波动由基准结果决定，不需要用户先选一个脱离测量的百分比。

## 只保留 nftables 后的边界

- 新建和安装内核节点只允许原生 nftables；运行环境不满足时明确报错，不转用任何 iptables 实现。
- 内核节点仍要核对 Agent 实际能力，不能只看数据库写了 nftables 就允许下发。
- 旧 iptables 节点不能靠改数据库字段变成 nftables 节点。若仍有旧节点，必须另行升级/迁移并验证；
  不支持的节点明确标记待迁移、拒绝相关控制操作，不静默转换、不删除历史账本。
- 新写入统一使用 `engine=kernel`。旧 `engine=iptables` 只兼容旧原生 nftables Agent 的控制协议名称，
  收到后归一为 `kernel`；不代表支持旧后端。`kernel_backend` 保留真实部署身份，旧 iptables 身份明确拒绝。
- 沿用 005 迁移及反迁移合同；不改 epoch、format 6/7、计数身份、账本、水位或额度。
- 对照和回滚版本固定为 `a08e3d8` 的 Java/原生 Agent，不把节点迁移与面板替换合成一次发布。

## 最重要的事务和切换约束

同一业务范围只能有一个写入者。初期 Go 影子实例读独立数据库快照，禁用后台任务、生产 Agent 连接和真实写操作；
不把写请求同时发送给 Java 与 Go。后续测试回放也对两份从同一快照恢复的数据库分别执行，比较结果，不能共库双写。

首发选择有边界的控制面整体切换，不做 Java/Go 按节点共库混跑。切换必须排空在途操作，
确保旧 Java 实例及其自动重启不会继续写库、接管 Agent 或运行任务；不能只切换 HTTP 入口。
用户级总额度跨节点共享，必须随面板完整交接，不能让 Java 与 Go 各自分配同一份额度。
若未来另行引入共库灰度，需要额外设计并验证可持久化、能拒绝旧实例继续写入的执行权机制，届时单独审查。
小时/每日任务和清理任务也必须有唯一执行权，禁止 Java/Go 双跑重置额度。

累计流量上报必须保持：校验 epoch/序号/累计水位 → 同事务去重、更新账本及相关额度 → 提交 → 才确认。
同一事务里的查询和更新使用同一个 `sql.Tx`，不可中途使用事务外 DB 连接。
删除与规则状态变更要处理“远端成功、面板提交失败/超时”的不确定性，以幂等 revision 和重连协调恢复，不能简单先改数据库再无条件记成功。
WS 超时、队列深度和每节点工作并发必须有界，避免一个失联节点阻塞全站，也避免重连风暴时无限创建 goroutine。

用户允许未来 GOST→内核迁移按某时点镜像流量，接受有限尾差；这不等于允许新 Go 面板在日常报告中重复记账或额度超发。
既有 TCP 会话不会因为重写面板而获得跨引擎无损迁移能力。Go 面板替换与节点引擎迁移分两次验收和部署。

## 验证与性能目标

复用本地缓存镜像、Maven 依赖和 Fusion Debian VM，所有业务测试只在隔离 veth/私有网络；不走 GZ 或任何生产转发入口。
Java 和 Go 使用相同的 CPU/内存限额、数据库样本、请求速率、节点/规则数量和报告周期，先热身再重复测量。
对比 API p50/p95/p99、错误/超时率、CPU、RSS、SQL 数量/锁等待、WS 命令完成时间和统计/额度积压；
覆盖日常少规则、1k/10k 规则、批次更新及报告重发风暴，记录原始结果和噪声范围。
把“全部保留功能通过、计费口径一致、配额不超发、操作与任务不重复执行”设为硬门槛。
第 0 批先测出 Java 基准与环境波动，再固定性能允许退化范围、长稳态时长和测试次数；
不事先承诺速度倍数，也不通过省略权限、计费或持久化来换性能。

## 未来切换与回滚（本次不执行）

先完成全部隔离验收，再基于当时实际生产版本、配置和数据库备份制定发布窗口。
回滚基线应是已完成 iptables 移除、通过 nftables-only 验证并与当时数据库迁移兼容的 Java 版本，
而非此前的双后端版本或任意更早版本。这个可回滚的 Java 基线是 Go 替换的前置条件。
Go 首版只加兼容结构；该 Java 基线必须能正确处理 Go 写入的数据、账本及待完成操作。
保留 Java 产物、配置与显式启动方法，并在隔离环境实际演练 Go→Java 回滚。
切换写入权时先阻止新管理变更，排空/确认在途账本事务，交接水位，停止旧任务与连接归属，再启用新方。
触发回滚时反向排空并归还写入权、重连 Agent、核对最新累计水位；保留最新数据库，不用旧备份覆盖切换后的合法账单。
需要恢复数据库备份时另列数据恢复步骤与可接受损失窗口，不能称其为普通代码快速回滚。

## 完成定义与执行边界

建立机器可读的功能/路由清单，每项必须对应实现与可执行测试；不以返回成功的占位接口、仅能编译或只通过旧测试代替完整实现。

验证码四种模式、OpenAPI、旧 GOST 命令加密、管理实时消息等同样必须覆盖，不得用“暂不支持”缩减已存在能力。
