## 建议决策

最终用一个 Go 面板进程替代 Java 后端，保留当前 React/Vite 前端、MySQL 数据和两类 Agent。
代码可以新写，验收按模块分批进行；首批不直接替换线上，不同时重做界面、数据库和节点协议。
Go 统一工具链及部署形式是可预期收益；内存、CPU、启动耗时和请求延迟的收益要用同环境测试确认，暂不承诺倍数。
面板语言变化不会直接提高已经在 Linux 内核中转发的业务吞吐。

采用模块化单体，建议目录 `panel-go/`，独立 `go.mod`；`node-agent/` 保持独立发布。
评审通过后再创建明确的重构分支，不在当前内核转发分支混入大量实现。
首期保持现有部署的前后端边界，最终可选一个 Go 可执行文件附带前端静态资产；不要求引入 Redis、消息队列或微服务。

## 实现结构

| 目录 | 职责 |
| --- | --- |
| `cmd/panel` | 配置、进程生命周期、启动/关闭 |
| `internal/httpapi` | HTTP 路由、校验、鉴权中间件、旧响应合同 |
| `internal/auth` | JWT、角色、授权和旧密码兼容适配 |
| `internal/domain` / `internal/service` | 用户、节点、隧道、规则、限速等业务约束 |
| `internal/store` | 显式 SQL、事务、条件更新、锁和幂等状态 |
| `internal/control` | Agent 连接注册表、请求/回执、会话与能力 |
| `internal/engine` | GOST / kernel 适配器；面板不管理本机 iptables/nftables |
| `internal/accounting` | 累计报告、额度预留/归还、账本事务 |
| `internal/jobs` | 有单一执行权的统计、重置、执法和协调任务 |
| `internal/release` | 安装配置、固定发布包及脱敏 |
| `tests/contract` / `tests/integration` | 双实现合同回放、真实 MySQL / Agent / 隔离内核测试 |

HTTP 先用标准库 `net/http`，事务用 `database/sql`；通过接口隔开 SQL 仓库和业务服务。
数据库驱动和 WebSocket 实现是在初期明确固定的必要依赖，不为减少依赖而手写驱动或 WebSocket 帧解析。
可评估复用 Agent 已使用的 WebSocket 库，但先核查维护情况和安全版本，再锁定依赖；不在方案阶段自动升级 Agent 工具链。
协议类型和规范化规则先用固定测试样本校验一致；只有确实稳定且无内核副作用的代码才考虑抽成共享包。

标准库依据：[HTTP](https://pkg.go.dev/net/http)、[事务](https://go.dev/doc/database/execute-transactions)、
[HTTP 测试支持](https://pkg.go.dev/net/http/httptest)。上述是建议的组织方式，不是官方对本项目架构的背书。

第 2 批“隧道 CRUD”和第 3 批“节点在线及规则下发”应分开验收：早期只用明确标注的连接夹具，
不能用伪在线状态声称真实转发通过。账本放在实现顺序后段，但其合同/边界在第 0 批就冻结。
Java 可能存在的不一致应记录并单独提出行为变更，不把现有错误一概复制，也不在兼容重构中悄悄改变计费口径。

## 最重要的事务和切换约束

同一业务范围只能有一个写入者。初期 Go 影子实例读独立数据库快照，禁用后台任务、生产 Agent 连接和真实写操作；
不把写请求同时发送给 Java 与 Go。后续测试回放也对两份从同一快照恢复的数据库分别执行，比较结果，不能共库双写。

真正灰度前需设计并验证可持久化、带防旧实例写入保护的执行权机制，按节点明确 WSS、流量上报、租约续期和规则操作的共同归属。
仅凭进程布尔开关或 HTTP 路由切换不够；若该隔离机制不能可靠落地，首发采用一次有边界的控制面整体切换，不强行在线混跑。
用户级总额度跨节点共享，按节点灰度不能拆成互不通信的额度账本；要么保留唯一额度服务写入者，要么整体切换该组写入。
小时/每日任务和清理任务也必须有唯一执行权，禁止 Java/Go 双跑重置额度。

累计流量上报必须保持：校验 epoch/序号/累计水位 → 同事务去重、更新账本及相关额度 → 提交 → 才确认。
同一事务里的查询和更新使用同一个 `sql.Tx`，不可中途使用事务外 DB 连接。
删除与规则状态变更要处理“远端成功、面板提交失败/超时”的不确定性，以幂等 revision 和重连协调恢复，不能简单先改数据库再无条件记成功。
WS 超时、队列深度和每节点工作并发必须有界，避免一个失联节点阻塞全站，也避免重连风暴时无限创建 goroutine。

用户允许未来 GOST→内核迁移按某时点镜像流量，接受有限尾差；这不等于允许新 Go 面板在日常报告中重复记账或额度超发。
既有 TCP 会话不会因为重写面板而获得跨引擎无损迁移能力。Go 面板替换与节点引擎迁移分两次验收和部署。

## 验证与性能目标

复用本地缓存镜像、Maven 依赖和 Fusion Debian VM，所有业务测试只在隔离 veth/私有网络；不走 GZ 或任何生产转发入口。
Java 和 Go 使用相同的 CPU/内存限额、数据库样本、请求速率、节点/规则数量和报告周期，先热身再重复测量。
对比 API p50/p95/p99、错误/超时率、CPU、RSS、SQL 数量/锁等待、WS 命令完成时间和统计/额度积压；
覆盖日常少规则、1k/10k 规则、批次更新及报告重发风暴，记录原始结果和噪声范围。
把“正确性完全一致、配额不超发、无副作用双执行”设为硬门槛；性能建议以 p95 无稳定超过 5% 的退化为初步门槛，
先用第 0 批基准判断 5% 是否高于环境噪声，再审定，不能为达数字跳过业务校验。

## 未来切换与回滚（本次不执行）

先完成全部隔离验收，再基于当时实际生产版本、配置和数据库备份制定发布窗口。
回滚基线应是已含节点后端选择与 004 兼容的 Java 版本，而非随意退到更早的线上旧版本。
Go 首版只加兼容结构；旧 Java 可读新版本写入的数据。保留 Java 产物、配置与显式启动方法。
切换写入权时先阻止新管理变更，排空/确认在途账本事务，交接水位，停止旧任务与连接归属，再启用新方。
触发回滚时反向排空并归还写入权、重连 Agent、核对最新累计水位；保留最新数据库，不用旧备份覆盖切换后的合法账单。
需要恢复数据库备份时另列数据恢复步骤与可接受损失窗口，不能称其为普通代码快速回滚。
