# v5.4 协议屏蔽与监听迁移验证

已实现 HTTP/TLS/SOCKS 的可选有界识别、UNKNOWN 放行及原因计数、旧 `[::]` 监听到 IPv4 云 NAT 场景的适配；两种内核后端保留。实现与识别边界见 [说明](forward-protocol-blocking.md)。本次没有修改、同步或部署任何线上环境，也没有使用 qcloud/GZ 入口。

## 功能结果

最终 ARM64 构建通过 55 个 Linux 引擎单元测试、7 组黑盒 / 152 次断言、Go 全模块竞态检测及 vet；Java 23 个单测和最终前端构建通过。真实 Spring Boot/MySQL 启动与节点创建 API 冒烟通过；它用于验证服务装配，Agent 数据路径另由私网真实内核测试验证。AMD64 交叉编译通过，未把 ARM64 虚拟机结果当作 AMD64 线上实测。

黑盒覆盖 HTTP/HTTP2、TLS、SOCKS4/5、私有 SOCKS5 认证 UNKNOWN、分段/大包前缀、未知透传、UDP、IPv6、OUTPUT、模拟 provider NAT、已有分类后的暂停、重启、有限 TCP/UDP 配额、被屏蔽正文不计费、最小权限 helper、队列占用失败/恢复、单条诊断对象回收、卸载和维护备份。helper 的长期权限保持 `0x3400`，不增加 SYS_ADMIN。

回归中修正了 NFQUEUE connmark 的 masked-XOR 写入：CTA_MARK 仅含 mask 内的判定位，不能重复填入高位 token。新测试明确要求所有被识别 TCP 保持完整 token，且未知 TCP 不能绕过有限 credit；旧错误构建被同一独立验证器拒绝。另覆盖了 netlink 最后一条属性/消息未补齐 padding、schema 0–4 不得夹带新策略、旧方括号重复拼接，以及真实启动发现的 Spring 依赖环（改为延迟注入）。

## 优化研究

已落地：完整首包可判定时，处理器微基准从 8400B/4 次分配降到 208B/2 次；只为不完整前缀建立重组缓冲。已判定允许的连接先检查 connmark 快速返回；UDP 直接在内核记 UNKNOWN；过期扫描最多每 50ms；UDP 诊断 counter 使用共享只读 GETOBJ 缓存，避免状态页逐规则启动 nft。微基准不包含 NFQUEUE syscall，不能把分配下降当作端到端吞吐同比提升。

真实软件 CPU 采样（单独诊断轮次，不混入性能结果）中，开启识别的稳态 Agent 样本约 74.9% 位于 Report 调用树、43.1% 位于 capture、25.1% 位于 JSON Marshal，识别线程约 1.4%。这些是包含子调用的比例，不能相加；共 283 个 cpu-clock 样本，说明本场景的主要剩余 Agent CPU 来自采样和持久化，而不是持续搬运业务数据。

建议下一步顺序：

1. 缓存已验证的 counter 身份，减少逐秒重复解码；将不变的规则定义与高频账本序列化解耦。必须保留先持久化再上报/ACK、epoch、GC 和恢复约束，并重做崩溃与掉电回归。
2. 优化冷连接：合并多个独立 verdict 的 netlink 写入，或按连接分片多个队列和状态锁；保护同连接顺序、500ms 上限和内核配额。不能简单按 TCP flags 跳过握手包，因为 TFO/乱序会改变识别边界。
3. 对已判缓存与待判前缀分别回收，减少大并发下扫描；再评估将识别判断合入既有 native hook，减少额外 hook 成本。必须保留协议丢弃先于配额/计数的顺序。
4. 面板源码另有逐转发查询 Node 配置的 N+1 路径，可改为每次对账的节点策略快照，并在事务提交后失效；此项是源码分析，未用 Agent 压测推算收益。

以上是后续优化方案，当前没有为追求峰值启用绕过暂停/配额/统计的 offload。
