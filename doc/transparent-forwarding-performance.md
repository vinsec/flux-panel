# Flux Panel 透明转发重构：性能与实现上的改进

> 更新：2026-11-02

我们在 Flux Panel 基础上保留 GOST，并增加原生 nftables 转发，两种方式由同一个节点管理程序控制。nftables 是 Linux 自带的包过滤与转发机制。

这次重构带来的收益，可以用三句话说明：**同样的流量，CPU 占用更低；规则多起来，业务包不必逐条寻找匹配；开启统计、配额和协议屏蔽后，持续传输仍尽量留在内核里完成。**

对于只有几条规则、日常下载和看视频的用户，收益主要是资源余量和转发开销更小。对于多用户、大量规则和频繁新建连接的节点，这些改动的价值更明显。

这里说的透明转发，是保留原来的访问入口和使用方式，由内核完成 TCP/UDP 端口转发。默认仍做地址转换，需要保留客户端 IP 时再按回程条件单独配置。

## 1. 最直接的收益：同样跑 150 Mbps，CPU 更低

3 条固定规则下，GOST 与原生 nftables 的对照结果如下：

| 重要指标 | GOST 转发 | 原生 nftables 转发 | 这组实测的变化 |
|---|---:|---:|---|
| 150 Mbps 时，整个测试核的 CPU 占用 | 11.43% | 8.69% | 约降低 **24%** |
| 150 Mbps 时，转发进程 CPU 占用 | 4.90% | 0.60% | 约降低 **88%** |
| 同一负载下，转发进程常驻内存 | 39.2 MiB | 15.6 MiB | 约降低 **60%** |
| 持续 TCP 往返延迟（中位数） | 0.136 ms | 0.113 ms | 约降低 **17%** |
| 持续 UDP 往返延迟（中位数） | 0.153 ms | 0.094 ms | 约降低 **38%** |
| 新建 TCP 连接到收到首个 64 字节回复（中位数） | 0.596 ms | 0.431 ms | 约降低 **28%** |
| 新连接首回复延迟（p95） | 3.412 ms | 2.706 ms | 约降低 **21%** |

**对日常使用来说，最有实际意义的是第一行：带宽照样跑满，留给其他任务的 CPU 更多。** 较低的进程占用也说明，程序少做了持续搬运业务数据的工作。25 Mbps 的低负载对照中，整核 CPU 为 3.60% → 3.19%，差距更小；轻负载本来就未必能明显感觉到变化。

## 2. 吞吐和连接能力：处理余量增加了

单连接上传、下载的处理速率也有明显提升：

| 指标 | GOST | 原生 nftables | 实测变化 |
|---|---:|---:|---:|
| 单连接下载处理速率 | 32.7 Gbps | 55.3 Gbps | 约提升 **69%** |
| 单连接上传处理速率 | 31.4 Gbps | 51.6 Gbps | 约提升 **64%** |

新连接方面，连续完成 10 万次“建连＋收到回复”的测试中，单出口 GOST 约为 1,103 次/秒，原生转发约为 10,047 次/秒。但这里的 GOST 后半程受到出口端口和连接状态积累的明显影响：它在压力尚未堆积时约为 6,000–7,000 次/秒；调整隔离测试的出口地址分布后，诊断结果约为 6,965 次/秒。

**原生转发对这种连接资源压力更从容。** 它不需要为每条会话额外建立一条由节点主动连接目标服务器的 TCP 连接，减少了建连和端口分配的工作。

下载和看视频通常由少量连接持续传输，并不会每传一个数据块就重新建连。新连接能力主要影响大量用户同时接入、批量探测、短请求和连接突发；它不是普通视频流畅度的唯一指标。

## 3. 规则多时，结构上的改进更重要

最初的内核转发方案为每条转发生成一组匹配、放行和计数规则。规则多了，一个业务包可能需要经过很长的检查列表。

对这两种规则组织方式进行对照，差异十分明显：

| 1,000 条规则 | 逐条匹配的方案 | 内核查表的方案 |
|---|---:|---:|
| 短传输处理速率 | 0.265 Gbps | 14.373 Gbps |
| 固定 150 Mbps 负载时，整组 CPU 占一核比例 | 53.30% | 6.18% |
| 一次原始计数导出耗时 | 155.03 ms | 12.57 ms |

这说明，**把转发放进内核之后，规则怎么组织依然很重要。** 只把每条业务翻译成几条防火墙命令，还不足以解决规则增多后的开销。

当前原生 nftables 使用查找表（map）：按入口地址、协议和端口直接找到业务，再找到转发目标和对应计数器。普通单目标转发增加配置时，主要增加表项，不需要让每个包依次试过全节点的业务规则。

统计也做了配套调整：流量统计直接从内核读取，省掉反复启动 `nft`、打印整张表、解析大段文本的工作。规则稳定时，还减少了重复验证、排序和编码。

后续针对 10,000 条规则继续优化后，同样开启协议识别，新连接完成速率从 9,006 提高到 9,502 次/秒，约提升 **5.5%**；规则编码这一步的耗时从 17.3 ms 降到 2.5 ms，约减少 **86%**。

## 4. 对比同类型项目：以 Forwardx 为例

[Forwardx](https://github.com/poouo/Forwardx) 是同类型的多用户转发面板，也通过独立的节点管理程序（Agent）控制转发。

两者的普通 nft 转发都由内核处理，配置下发都会使用外部命令。我们的重点改进在于：**内核里的规则怎么查、统计怎么读、开启增强功能后数据怎么走。**

| 比较点 | Forwardx | 本项目的实现及收益 |
|---|---|---|
| 业务规则如何组织 | 为每条转发生成独立 nft 规则 | 普通转发用查找表分发，避免按全节点规则逐个寻找业务 |
| 核心规则如何更新 | 生成清理、删除、添加的命令序列 | 核心转发规则整批更新，配合保护和恢复流程，减少规则只改了一半的情况 |
| 业务字节如何采样 | 调用命令导出整张规则表，再解析文本中的规则与计数 | 直接读取内核计数，减少启动外部程序和解析整表文本的开销 |
| 协议策略、限速相关路径 | 通过连接代理程序（Guard）接受连接、连接目标，再由 Go 程序持续收发数据 | 协议识别只处理有限的连接前缀；识别后回到内核，平滑限速由内核队列执行 |

最后一行对持续下载尤其重要：识别开头之后，后续大文件不必始终由 Go 程序在两个连接之间转运。我们还把普通新连接进入识别程序的次数从三次减少到两次，让不携带业务数据的确认包直接在内核中通过。

Forwardx 同样具备持久化上报、失败重试和报告去重。我们的改进进一步覆盖了内核查表分发、直接读取内核计数，以及协议识别后回到内核的持续传输路径。对于长期下载和规则较多的节点，这些都是有实际意义的结构差异。

源码依据：[Forwardx 规则生成](https://github.com/poouo/Forwardx/blob/bf972f3c7d29cbcf241690bb25dc9dc8a889e926/server/agentActionCommands.ts#L355)、[计数采样](https://github.com/poouo/Forwardx/blob/bf972f3c7d29cbcf241690bb25dc9dc8a889e926/agent/metrics.go#L2832)、[连接代理的收发实现](https://github.com/poouo/Forwardx/blob/bf972f3c7d29cbcf241690bb25dc9dc8a889e926/agent/main.go#L12669)。

## 5. 这些收益，保留了哪些日常能力

这次重构同时处理了转发、计费和恢复，日常使用方式也延续下来：

- **下载、视频持续传输**：数据主要在内核里通过，减少持续用户态收发；协议屏蔽按已验证的识别范围工作，未知流量按既定规则放行。
- **暂停、额度和到期**：在节点本地检查，暂停也约束已有连接。有额度的规则在面板失联后受已发额度及有效期限制，不能无限等待下次同步才停流。
- **统计和账本**：累计计数、上报确认、去重和恢复有完整流程；重启、规则删除和模式切换都有对应验证，不依赖简单清空计数重新开始。
- **域名、IPv4/IPv6、TCP/UDP 和限速**：保留统一管理与计费，原生转发能够承接实际业务配置。
- **权限和维护**：联网 Agent 没有修改内核网络配置的权限，必要操作交给权限受限的本机辅助进程；同一套节点管理程序可在原生 nftables 和受管 GOST 之间切换，节点身份与累计账本能够延续。切换允许短暂中断，现有连接需要重连。

加入统一管理和模式切换后，再次验证了 3 条和 10,000 条规则下的持续传输，两组都达到设定的 150 Mbps，新连接处理能力与整合前基本持平。
