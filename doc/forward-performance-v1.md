# GOST / iptables v1 性能验证（2026-10-25）

被测引擎基线 `58eba4a`。此次只新增测试工具，没有修改引擎实现，也没有上线新版本。

结论：少量规则下 iptables 有提升，但当前逐规则实现存在明显规模退化，不能作为普遍更快的 GOST 替代品。

## 环境与方法

qcloud-sg 的一次性 Docker 容器使用 `--network none`，限制 512 MiB、0.75 核、低 CPU 权重及 nice 19。client/router/target 均为容器内 netns，经 MTU 1500 的私有 veth 通信，root 与 router 无外部默认路由；没有使用广州入口或公网压测。线上容器的 ID、镜像、启动时间保持不变。

控制器 CPU 0，数据端点与转发器 CPU 1。GOST/Agent 均 GOMAXPROCS=1，开启 5 秒业务流量统计。三轮交替顺序，规模组热点默认排在规则末端，另测前置情况。

正式 TCP 工具等待接收端收齐全部 64 MiB 并返回回执才结束计时，三轮中位数如下。早期 iperf3 短流发送/接收统计边界不一致，已排除其 TCP 主表；UDP、应用回声延迟独立分析。

| 转发数 | GOST 短传输 Gbps | iptables 短传输 Gbps | GOST 进程组核秒/GiB | iptables 进程组核秒/GiB |
|---:|---:|---:|---:|---:|
| 2 | 9.59 | 13.14 | 1.018 | 0.762 |
| 100 | 7.06 | 3.35 | 1.150 | 2.401 |
| 1000 | 8.49 | 0.255 | 1.115 | 25.784 |

以上为短传输处理能力，不是持续公网带宽。进程组 CPU 包含端点与控制器，不是单独转发器归因；另外记录 CPU 1 的 system/softirq 等工作，规模退化方向一致。共享主机有后台噪声，同速率补充样本不能精确归因整机 CPU 节省。

2 条转发的长连接 TCP 应用 RTT p95：GOST 0.312 ms、iptables 0.238 ms；1000 条时变为 0.290 ms、1.594 ms。该绝对差值仅反映无物理链路延迟下的虚拟路径，不代表公网 RTT 能同比下降。

50 Mbps / 1200 字节 UDP 和 5 Mbps / 64 字节 UDP 两种模式基本达标，没有据此测出 UDP 峰值容量。

## 瓶颈判断

与代码结构一致的推断：`rules.go` 为每条转发生成 mangle 分类和 FORWARD 双向计数/放行规则，已经标记的连接仍会遍历分类链，热点后置时每包成本随规则数增长。1000 条转发约对应 2000 条分类规则与 4000 条 FORWARD 规则。尚未用 perf 做进一步采样归因。

热点前置的单轮 16 MiB 回执诊断中，GOST 8.00 Gbps、iptables 0.870 Gbps；虽有改善仍明显落后，不应只靠把热门规则排前来解决。

下一步应先设计首次分类与后续连接标记快速分发，并评估从逐条规则计数改为内核连接计数聚合，同时保留暂停/配额强制路径。此次没有优化或关闭这些功能来影响数字。

可复现的测试源码与指标定义见 [性能工具文档](../node-agent/tests/benchmark/README.md)。完整分阶段应用负载累计约 4.982 GiB，低于调整后的 5 GiB 上限，全部为同机虚拟网络数据，不含依赖下载和 SSH 传输。
