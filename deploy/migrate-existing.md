# 从旧版本迁移

推荐顺序：**先换面板，暂留旧 GOST 节点；再选一台节点试迁；验收通过后分批推广。** 不必一次更换所有节点。

目标是保留账号、余额、授权、规则、访问入口和切换时点的累计流量。节点切换会断开已有连接，客户端需要重连，请预留维护窗口。

## 1. 先确定你属于哪种情况

| 当前情况 | 处理方式 |
|---|---|
| 旧面板＋独立 GOST 节点 | 先迁移面板，继续管理原节点；之后再决定哪些节点改用统一 Agent |
| 由本仓库脚本安装的 Go 面板 | 先备份，再更新，见下面的命令 |
| 手工部署、外部数据库或定制版本 | 按实际配置迁移，不套用默认容器名和数据库地址 |
| 已经使用统一 Agent | 保留原配置、状态和密钥，按升级流程处理；不要当作新节点重新初始化 |
| 旧 iptables 内核节点或不明来源版本 | 先用原程序结算、备份并检查状态，再制定转换方案，不直接覆盖 |

面板的 WSS 管理连接与业务本身使用的 TLS/WSS 隧道是两回事。旧业务隧道可以先保留在旧节点，不能假设全部都能原样转换为内核转发。

## 2. 停机前准备好

- 记录当前面板、数据库、节点的启动方式和实际配置，盘点规则、业务端口、协议屏蔽、限速、DNS／IPv6 和特殊路由。
- 备份数据库、配置、旧镜像／程序、服务文件及节点状态，确认备份可以在独立测试环境恢复。
- 提前准备新镜像、面板生成的节点安装命令，以及只针对本次对象的切换、验收和回滚步骤。不要停机后才开始下载、编译。
- 选定试点节点、维护窗口和最长允许中断时间；超时就回退，不带着故障继续迁下一台。

先在独立数据库和私有目标上演练。密码、密钥与完整备份保存在权限受限的文件中，不贴到公开页面。

## 3. 先迁移面板

### 原有面板不是本仓库脚本创建的 Go 安装

| 顺序 | 操作 | 怎样算完成 |
|---|---|---|
| 1 | 用数据库副本验证新程序，提前构建镜像 | 用户、规则、权限和累计值能正确读取，尚未连接真实节点 |
| 2 | 新部署沿用原数据库、域名、JWT 配置和时区 | 不会新建空库替代原库；部署参数已核对 |
| 3 | 进入窗口，停用旧面板写入、自启动和定时任务，做最终备份 | 确认旧面板已停止写库 |
| 4 | 执行增量迁移，再启动新面板 | 登录、健康检查和节点重连正常 |
| 5 | 核对数据与实际业务 | 只有新面板在写库，账号、规则、余额和累计值保留 |

已有数据库使用 `migrate`，**不能加 `--init`，也不要用新装命令接管旧库**。确认新镜像、数据库和网络配置正确后，命令形式如下：

```sh
docker compose run --rm --no-deps backend migrate
docker compose up -d --no-build --wait backend frontend
```

实际部署如果有 `-f`、`--env-file`、自定义项目名或服务名，要保留这些参数。外部数据库继续使用原连接和备份方式，不为了匹配示例改动现有数据库。

新旧面板不能同时写同一个库。原 GOST 节点可先保留，但仍需验证它们的业务和统计，不能只看面板能登录。

### 已由本仓库脚本安装的 Go 面板

在原安装目录执行：

```sh
./panel_install.sh backup
git pull --ff-only
./panel_install.sh update
```

上述备份命令适用于脚本创建的内置数据库；外部数据库使用自己的备份方式。迁移失败时保持后端停止，先排查原因，不自动让旧程序重新写库。

## 4. 再试迁一台节点

优先选择规则简单、用户少、允许短暂停机的节点。面板自带安装文件，常规命令从节点的“安装”弹窗取得，见 [节点安装](../node-agent/README.md)。

**旧独立 GOST 转成统一 Agent，目前还需要针对实际部署转换节点和隧道记录，安装器不会自动完成这一步。** 编辑节点也不允许直接更换程序类型。应先生成专用转换与恢复步骤，保留原 ID、密钥、规则、入口、授权和累计流量，只更新已核对兼容的相关记录。不要批量把全库节点改成内核模式。

| 顺序 | 操作 | 验收／失败处理 |
|---|---|---|
| 准备 | 核对全部规则兼容性、端口、依赖和回程，保存原记录与服务状态 | 有不兼容项就保留旧节点，暂不切换 |
| 保护 | 暂停本次节点的配置变更，记录切换时点，设置独立超时回滚 | 管理连接丢失后也能回退，不影响其他节点和管理端口 |
| 停旧 | 停止旧 GOST 和会自动拉起它的任务 | 同一业务入口不会被两套程序同时接管 |
| 转换、安装 | 执行已核对的记录转换，安装统一 Agent，等待原规则生效 | 节点完成注册，规则确实落地 |
| 验收、收尾 | 验证实际业务与额度，取消临时保护和回滚定时器，确认自启动 | 通过后观察，再迁下一台；关键项失败或超时则回退 |

普通端口转发可优先评估原生 nftables；特殊业务隧道或不兼容策略可继续使用旧 GOST。受管 GOST 的特殊路由、源地址保留和带限速规则也要单独检查，不把“可切换”理解为所有配置都能互换。

不清空整机连接表、防火墙或其他服务规则，不删除数据库卷。只对本次迁移明确拥有的对象操作。

## 5. 流量接续与验收

保留切换时点的原累计值，新程序继续记录切换后的新增量。旧 GOST 应用字节与统一 Agent 网络层字节口径有区别，切点前后的每个字节不要求完全相同，但不能重置用户余额或把历史总量重复计入。

至少检查：

- 管理员和普通有配额用户都能使用，实际 TCP／UDP 及用到的 DNS／IPv6／限速／协议屏蔽正常。
- 有限额度持续自动续期，至少跨两个续租周期观察；暂停及额度耗尽等边界用隔离环境或专用测试账号验证。
- 累计流量正常新增，重连和服务状态正确；不能仅凭“在线”或“服务运行中”验收。

业务验证只用明确允许的少量流量，不自动测速或通过收费入口跑量。

## 6. 失败时怎么退

| 失败阶段 | 回退方式 |
|---|---|
| 尚未切换 | 继续使用旧系统，修复演练问题 |
| 已换面板，节点仍全部是旧 GOST | 停止新写实例，确认数据库兼容与最新数据后，按已验证方案恢复旧面板 |
| 节点试迁失败，尚未正式放行业务 | 停新进程，处理已产生的用量和额度预留，恢复该节点的原记录、旧服务及入口 |
| 已有统一 Agent 正式运行 | 优先保留新面板和 Agent，切回此前验证过的模式；退回旧程序需另行结算和转换 |

回退程序不等于恢复旧整库。新增账单及其他节点的数据要保留，新状态不能直接交给旧程序读取；也不能只改回节点标签、覆盖状态文件后就启动旧服务。
